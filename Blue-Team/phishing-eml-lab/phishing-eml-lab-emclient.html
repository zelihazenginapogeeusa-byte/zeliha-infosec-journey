📧 Phishing .eml Lab — eM Client Walkthrough ☀ A self-contained header-forensics lab for eM Client — three original, purpose-built .eml samples with planted red flags, no external repo required. The process, at a glance 1 Get the sample Download one of the 3 custom .eml scenarios from your own repo. → 2 Install & open eM Client Free download, then drag the .eml into a local folder. → 3 Show Source Pull the full raw headers — this is where the real investigation starts. → 4 Fill the header table From, Reply-To, Return-Path, Received chain, SPF/DKIM/DMARC. 5 Extract links Compare displayed text vs. real href in the raw source. → 6 Check VirusTotal Paste the extracted URLs/IPs/hashes, check reputation. → 7 Write the triage report 4–5 line SOC Tier-1-style summary of the verdict. Step by step 1 Get the sample Download the target .eml file from your own zeliha-infosec-journey repo — three original scenarios, purpose-built for this lab, each with a specific set of planted red flags. Sample Scenario Download sample-01-it-helpdesk-reset.eml Credential-harvesting — fake IT helpdesk password-expiry notice ⬇ download sample-02-invoice-overdue.eml Vendor / BEC-style — fake overdue invoice with a "changed" remittance account ⬇ download sample-03-account-suspended.eml Urgency / account-takeover — fake "unusual sign-in blocked" cloud-storage alert ⬇ download Each link opens the file on GitHub — use the Download raw file button there (the ⬇ icon in the file view) to save it locally. 2 Install eM Client, then open the sample eM Client is a free desktop email client — the free version is enough for this, nothing paid is required. Download: emclient.com/download (Windows) or emclient.com/download-mac (Mac) Run the installer → open eM Client → skip/close the "add an account" prompt if you don't want to connect a real mailbox, you don't need one for this lab. Then drag the downloaded .eml file directly into a local folder inside eM Client (or File → Open). It opens like a real received email. 3 Pull the raw headers — the step that actually matters The normal message view only shows you a summary. The real investigation happens in the raw source. Right-click the email → Show Source (same option is also reachable from the message menu). This opens the full raw MIME source — every header, unfiltered. 4 Fill in the header table Work through the raw source and record each field — this table doubles as your worksheet: Field Where to find it in the raw source From address From: header — check it matches the display name Reply-To Reply-To: header — a mismatch from From is a classic red flag Return-Path Return-Path: header — where bounces actually go, often reveals the real sending domain Received chain Stack of Received: headers, read bottom-to-top — traces the actual server hops back to origin SPF / DKIM / DMARC Authentication-Results: header — look for pass / fail / none on each Subject / Date / Message-ID Standard headers near the top of the source 5 Extract the suspicious links This is the one step eM Client alone doesn't handle as cleanly as VS Code + grep. In the normal message view, hover a link and check the status bar for the real destination. But when the visible text and the actual target need a side-by-side check, go back to the Show Source view from Step 3 and read the raw tags directly — that's the only way to catch a link whose displayed text doesn't match where it actually goes. Hybrid approach, by design: eM Client for the email and header investigation, raw source (or a plain text editor, if you export it) for pulling out real URLs, VirusTotal for reputation checks. This isn't a workaround — it mirrors how a real SOC Tier 1 analyst actually works. 6 Check IOCs against VirusTotal Copy each extracted URL, IP, or attachment hash into VirusTotal and check the detection ratio and any tagged behavior — same as any other IOC reputation check. 7 Write the triage report Close it out with a short SOC Tier-1-style summary: who it claims to be from, which authentication checks failed, which IOCs came back malicious/suspicious, and your verdict (malicious / suspicious / benign). Reuse the phishing investigation playbook and report template already in your Blue-Team folder for the exact structure. How to prove an email is malicious No single red flag is proof on its own — a typo or an ugly template doesn't make an email malicious. A defensible verdict comes from correlating multiple independent signals across the headers, the body, and external verification. Below is what to actually check, and what "proof" looks like at each layer. 8 Header-level evidence Signal Where to look Why it counts as evidence Authentication failure Authentication-Results: header spf=fail / dkim=fail / dmarc=fail on a mail claiming a real, established domain means the sending server was never authorized to send as that domain From / Reply-To / Return-Path mismatch Compare all three headers side by side Legitimate mail rarely routes replies or bounces to a completely different domain than the one it claims to be from Received chain doesn't match the claim Bottom-most Received: line = first real hop If that IP/hostname has no relation to the claimed sender (check via WHOIS/rDNS), the message didn't originate where it says it did Display name masking the real address From: header — display name vs. the actual email address A trusted-looking display name hiding an unrelated address is a classic spoofing/lookalike tactic Message-ID domain mismatch Message-ID: header Generated by a mail system on a completely different domain than the one the email claims to be from 9 Body-level evidence Signal Where to look Why it counts as evidence Displayed link text ≠ real destination Raw source — compare text to its href= Deliberate visual deception; one of the single strongest indicators when found Suspicious destination type The actual href target A raw IP address, a URL shortener, an unusual/newly-seen TLD, or a lookalike domain (extra word, extra hyphen, swapped TLD) of the real brand Urgency + credential/payment request combo Overall body language Legitimate organizations rarely combine "act within X hours" with "click here to verify / pay now" in the same message Attachment type MIME part / file extension .html, .js, .vbs, .iso, .lnk, or macro-enabled Office files (.docm/.xlsm) are almost never sent legitimately and are common malware droppers 10 External verification — this is what turns "suspicious" into "confirmed" Signal Where to check Why it counts as evidence URL / IP / attachment hash reputation VirusTotal Multiple independent engines flagging the same indicator as malicious is third-party confirmation, not just your opinion Domain age WHOIS (e.g. whois.domaintools.com) A domain registered days or weeks ago while impersonating an established brand is a strong tell — real vendors don't rotate domains that often Sending IP reputation / ownership AbuseIPDB, ASN / reverse-DNS lookup IP sits on a consumer ISP or unrelated hosting, with no connection to the claimed organization's real infrastructure Attachment behavior Sandbox only — ANY.RUN, Joe Sandbox, Hybrid Analysis (never open it locally) Confirms actual malicious behavior — dropped files, C2 callbacks — instead of just static suspicion What actually counts as "proof": one failed SPF check alone is not proof — plenty of legitimate mail fails SPF due to ordinary misconfiguration. A defensible malicious verdict comes from convergence: e.g. domain impersonation + failed DKIM/DMARC + a link resolving to a raw IP + that same IP/URL flagged malicious on VirusTotal. When you write the triage report, cite the specific header/body evidence together with the external confirmation — that combination is what "proof" means in a real SOC handoff, not a gut feeling.
