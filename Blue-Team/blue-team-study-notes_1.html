General Approach

  • Investigation strategy & workflow

    A few habits that make every module below faster to apply once you're in a real scenario.

    • Read through everything you're given first, to understand the full scope before diving in.
    • Prioritize high-impact leads: phishing email → initial access host → SIEM time window → Autopsy / Event Logs → PCAP.
    • Document continuously in a timeline — IOCs, timestamps, tools used, conclusions (see the note-taking format under "Timeline / Note-taking Method" further down).
    • Map findings to MITRE ATT&CK where relevant.
    • Time-box your deep-dive analysis — investigation windows disappear faster than you'd expect.
    • Keep your own notes fast to search — you'll be referencing them constantly.
    • If you're short on time, prioritize: Wireshark, Splunk, phishing analysis, DeepBlueCLI, Autopsy.
  • Answer / report format template

    Whether it's a phishing verdict or a full IR write-up, structuring your answer the same way every time makes it faster to write — and easier for a grader to follow. A reliable skeleton:

    1. Summary — one or two sentences: what happened, your verdict (malicious/benign/suspicious), overall severity.
    2. Findings / Timeline — the key events in order, each with timestamp + source, pulled straight from your running timeline (see "Keep a living investigation timeline" further down).
    3. IOCs — a clean table: type, value, source, notes (same format as the phishing IOC table under "Phishing Analysis Fundamentals").
    4. MITRE ATT&CK mapping — tactic/technique IDs for what you observed, e.g. Initial Access – T1566 Phishing.
    5. Recommended actions — specific and actionable: "block domain X at the firewall," "disable account Y," "isolate host Z" — not vague advice.
    6. Lessons learned (when the scenario calls for it) — what control gap allowed this, and what would prevent it recurring.

    Example opening line: "On [date/time], user [X] received a phishing email impersonating [brand] that led to execution of [file/technique] on host [Y]. The activity is assessed as malicious with [confidence] confidence based on [key evidence]." Leading with a sentence like this signals you understood the scenario before the grader reads another word.

Cyber Defense Frameworks

  • Junior Security Analyst Intro
    Orientation only — sets expectations for the SOC analyst role, not a technical topic itself.
  • Pyramid of Pain
    Ranks IOC types by how hard they are for an attacker to change — helps you prioritize what's worth detecting/blocking (hashes are trivial to change, TTPs are painful).
  • Cyber Kill Chain
    The standard model for breaking an intrusion into stages — you'll use it constantly to explain where in an attack something was caught.
  • Unified Kill Chain
    Merges the Kill Chain with MITRE ATT&CK into one lifecycle — useful for mapping attacks that loop back through stages (e.g. repeated lateral movement).
  • Diamond Model
    Frames an intrusion as Adversary–Infrastructure–Capability–Victim — a useful structure for attribution and pivoting between indicators.
  • MITRE (ATT&CK)
    The universal reference for adversary tactics and techniques — nearly every tool, report, and later BTL1 module maps back to it. Tool: attack.mitre.org / ATT&CK Navigator for mapping and visualizing what you've found.

  • Wireshark: Traffic Analysis

    Applies Wireshark to real attack traffic — the applied skill, not just the tool interface.

    Host / IP

    ip.addr == 10.0.0.5
ip.src == 10.0.0.5
ip.dst == 185.x.x.x
!(ip.addr == 10.0.0.0/8)

    Ports

    tcp.port == 4444
tcp.dstport == 8080 || tcp.dstport == 443
udp.port == 53

    DNS

    dns.qry.name contains "evil"
dns.qry.name.len > 50
dns.qry.type == 16
dns.flags.response == 0

    HTTP

    http.request.method == "POST"
http.request.uri contains "gate" || http.request.uri contains "panel"
http.user_agent contains "python" || http.user_agent contains "curl"
http.response.code >= 400
http && frame.len > 10000

    SMB

    smb || smb2
smb2.filename contains ".exe" || smb2.filename contains ".ps1"
smb2.filename contains "ADMIN$" || smb2.filename contains "C$"

    Suspicious patterns

    tcp.flags.syn == 1 && tcp.flags.ack == 0
ip.dst == <suspected_c2>
frame.len > 1400 && tcp

    TLS / SSL

    tls.handshake.type == 1                          # Client Hello — check the SNI for the real destination domain
tls.handshake.extensions_server_name contains "evil"
tls.handshake.type == 11                         # Server certificate — check issuer/validity
ssl.record.version == 0x0301                     # unusually old TLS version, sometimes a red flag

    Even without decrypting, the JA3/JA3S fingerprint of the TLS handshake can identify known malware families — worth checking against a JA3 blacklist if you suspect C2 over HTTPS.

    Kerberos (Active Directory attacks)

    kerberos && tcp.port == 88
kerberos.CNameString
kerberos.msg_type == 10                          # AS-REQ — relevant when hunting AS-REP roasting / Kerberoasting attempts

    ARP / ICMP

    arp.duplicate-address-detected                   # possible ARP spoofing
icmp.type == 8 && data.len > 64                  # oversized ICMP payloads can indicate ICMP tunneling

    FTP (cleartext credentials)

    ftp.request.command == "USER" || ftp.request.command == "PASS"

    TCP health / anomalies

    tcp.analysis.retransmission
tcp.analysis.zero_window

    tshark — command-line Wireshark

    Useful when you don't have the GUI, or want to script extraction against a large capture:

    tshark -r capture.pcap -Y "http.request" -T fields -e ip.src -e http.host -e http.request.uri
tshark -r capture.pcap -Y "dns" -T fields -e dns.qry.name | sort -u
tshark -r capture.pcap --export-objects http,./extracted/

    Patterns worth hunting

    • Regular small outbound connections (beaconing) — plot with Statistics → IO Graph, look for evenly spaced spikes
    • Large outbound data transfers to unusual destinations
    • Long or random DNS subdomains / high volume of TXT records (possible DNS tunneling) — Statistics → DNS gives a quick top-queried-domains view
    • SMB lateral movement indicators
    • Non-standard ports or empty/odd User-Agents
    • TLS handshakes with unusual JA3 fingerprints or self-signed/expired certificates

Phishing

  • Phishing Analysis Fundamentals

    The foundation for the entire Phishing Analysis section — headers, artifacts, verdicts. Full workflow:

    1. Defang immediately

    Convert http → hxxp and . → [.] before any lookup or paste, so you never trigger a live link.

    2. Header analysis (highest priority)

    • Trace the full Received: chain bottom to top → true originating IP.
    • Compare From:, Return-Path:, Reply-To:, Sender: for mismatches.
    • Check SPF / DKIM / DMARC results — brand impersonation + DMARC fail is a strong spoofing signal.

    3. Body & social engineering

    • Identify the pretext (invoice, lockout, delivery, IT/HR helpdesk, urgency).
    • Extract every URL — visible text vs. actual hyperlink.

    4. URL & attachment analysis

    • Expand shortened links, check VirusTotal / urlscan.io / AbuseIPDB, watch for typosquatting.
    • Hash attachments (MD5/SHA1/SHA256) and submit to VirusTotal or a sandbox.

    5. Consolidate IOCs

    TypeValueSourceNotes
    Sender IPx.x.x.xReceived header…
    Domainevil[.]comFrom / URL…
    File hashabc123…AttachmentSHA256 preferred

    6. Defensive actions & reporting

    Recommend blocking domains/IPs/hashes, map to MITRE ATT&CK (Initial Access – Phishing T1566), then write a short structured report: summary, IOCs, analysis steps, verdict, recommended actions, lessons learned.

    Example recipe — decoding an encoded PowerShell command

    PowerShell's -enc / -EncodedCommand flag takes Base64 of UTF-16LE text, not plain UTF-8 — so a single "From Base64" step gives you garbage with null bytes between characters. Two-step recipe:

    Recipe:  From Base64  →  Decode text (UTF-16LE (1200))
Input:   JABjAGwAaQBlAG4AdAAgAD0AIABOAGUAdwAtAE8AYgBqAGUAYwB0ACAA...
Output:  readable PowerShell source

    Other recipes worth keeping bookmarked: URL Decode → Remove whitespace for messy phishing links, and the Defang URL / Fang URL operations for safely pasting IOCs into a report without them being clickable.

Section 5 - Digital Forensics

Forensics Fundamentals

  • File Systems

    Understanding NTFS/EXT basics is what makes artifact locations later make sense. Key Windows paths you'll navigate constantly inside Autopsy:

    C:\Windows\System32\config\      → SYSTEM, SOFTWARE, SAM, SECURITY, DEFAULT hives
C:\Windows\Prefetch\             → Prefetch files
C:\Windows\System32\winevt\Logs\ → Event Logs (.evtx)
C:\Windows\AppCompat\Programs\Amcache.hve
C:\Users\<username>\             → NTUSER.DAT
...\AppData\Local\Microsoft\Windows\UsrClass.dat
...\AppData\Roaming\Microsoft\Windows\Recent\ → LNK files, Jump Lists
  • Order of Volatility
    Determines what you collect first during live response — get this wrong and you lose evidence. High → low: registers/cache → RAM → network state / running processes → disk → backups / remote logs.
  • Metadata and File Carving
    Core technique for recovering and dating evidence from disk images — relevant filesystem structures: $MFT, USN Journal ($J), and Alternate Data Streams.
  • Hashing and Integrity
    Every piece of evidence you collect needs to be hashed to prove it wasn't tampered with. Prefer SHA256, hash before and after export, and record the tool + hash in your timeline. Commands: sha256sum <file> / md5sum <file>.
  • Data Representation, HDD/SSD Basics
    Useful background on how storage actually works, rarely the direct subject of a question.

Digital Evidence Collection

  • Chain of Custody
    Evidence handling is graded — a technically correct finding with a broken chain of custody is a weak answer.
  • Disk Imager: FTK Imager
    The standard tool for creating forensic disk images — expect to use it hands-on for image mounting and review.

    kape.exe --tsource C: --tdest E:\Evidence --tflush --target !SANS_Triage

Windows & Linux Investigations

  • Windows Artifacts - Programs

    Prefetch, shimcache, and similar — the go-to evidence for "was this program executed."

    • Prefetch — C:\Windows\Prefetch\*.pf — run count + last 8 timestamps (often disabled on servers)
    • Amcache — C:\Windows\AppCompat\Programs\Amcache.hve — includes SHA1, great for VirusTotal pivots
    • ShimCache / AppCompatCache (SYSTEM hive) — historical presence
    • UserAssist (NTUSER.DAT) — GUI-launched programs
    • BAM/DAM (Windows 10+)

    EZ Tools command examples

    These are Eric Zimmerman's tools — free, and the standard way to turn raw artifacts into a clean CSV you can pivot in Excel, Timeline Explorer, or re-ingest into Splunk:

    # Prefetch — PECmd
PECmd.exe -d "C:\Windows\Prefetch" --csv "C:\output" --csvf prefetch.csv

# Amcache — AmcacheParser
AmcacheParser.exe -f "C:\Windows\AppCompat\Programs\Amcache.hve" --csv "C:\output"

# ShimCache / AppCompatCache — AppCompatCacheParser
AppCompatCacheParser.exe -f "C:\Windows\System32\config\SYSTEM" --csv "C:\output"

    Parsing tools: PECmd, AmcacheParser, AppCompatCacheParser, ProcDump for live process memory. Triage priority: Prefetch + Amcache + key Event Logs + UserAssist for a quick picture of what executed and when.

  • Windows Artifacts - Browsers

    Browser history/downloads are frequently the pivot point in phishing-to-compromise chains.

    • LNK files — %AppData%\Microsoft\Windows\Recent\
    • Jump Lists — ...\Recent\AutomaticDestinations\ and CustomDestinations\
    • ShellBags, RecentDocs / MRU

    EZ Tools command examples

    # LNK files — LECmd
LECmd.exe -d "C:\Users\<user>\AppData\Roaming\Microsoft\Windows\Recent" --csv "C:\output"

# Jump Lists — JLECmd
JLECmd.exe -d "...\Recent\AutomaticDestinations" --csv "C:\output"

    Tools: Browser History Capturer / Viewer, JumpList Explorer, Windows File Analyzer for LNK shortcuts.

  • Windows Artifacts - Recycle Bin
    A classic "attacker tried to hide something" artifact — look for the paired $I (metadata) and $R (actual file) entries. Small topic, commonly tested.
  • Linux Artifacts: Passwd and Shadow
    Where you check for unauthorized accounts or privilege changes on a Linux host — awk -F: '($3==0){print}' /etc/passwd for UID 0 accounts, grep -E 'sudo|wheel' /etc/group for privileged users. Full Linux forensics cheat sheet is under "Linux Forensics" above.
  • Linux Artifacts: /Var/Lib and /Var/Log
    The Linux equivalent of Windows Event Logs — /var/log/auth.log (Debian/Ubuntu) or /var/log/secure (RHEL/CentOS) for logon activity, /var/lib/ for package and service state.
  • Linux Artifacts: User Files, Memory
    Useful supplementary evidence once you already know where the primary logs are — ~/.bash_history, ~/.ssh/, cron/systemd persistence.

Memory & Disk Analysis

  • What is Volatility? / Volatility Walkthrough

    Memory analysis catches things disk forensics never will — a genuinely different, essential skill. Labs may use Volatility 2 (needs --profile=) or Volatility 3 (no profile) — keep both syntaxes ready.

    Volatility 2

    volatility -f memory.dmp imageinfo
volatility -f memory.dmp --profile=PROFILE pslist
volatility -f memory.dmp --profile=PROFILE pstree
volatility -f memory.dmp --profile=PROFILE netscan
volatility -f memory.dmp --profile=PROFILE malfind
volatility -f memory.dmp --profile=PROFILE cmdline
volatility -f memory.dmp --profile=PROFILE filescan

    Volatility 3

    vol -f memory.dmp windows.info
vol -f memory.dmp windows.pslist
vol -f memory.dmp windows.pstree
vol -f memory.dmp windows.netscan
vol -f memory.dmp windows.malfind
vol -f memory.dmp windows.cmdline
vol -f memory.dmp windows.filescan

    Recommended order

    1. pslist/pstree — odd parents, short-lived processes, suspicious names
    2. netscan — external connections and unusual ports
    3. malfind — injected code regions
    4. cmdline/dlllist on interesting PIDs, then dump for further analysis
  • Volatility 3 / Volatility Workbench
    The current tooling you'll actually be using — worth practicing over the older Volatility 2 workflow. See the full command set under "What is Volatility?" above.
  • What is Autopsy? / Autopsy Walkthrough

    The GUI disk-forensics tool you'll rely on for full disk-image investigations.

    Basic workflow

    1. Create a new case → Add Data Source (disk image / E01 / raw).
    2. Select relevant Ingest Modules — Recent Activity, File Type Identification, Hash Lookup (skip running everything on large images if time is limited).
    3. Use Keyword Search, Timeline, and Extracted Content views heavily.
    4. Right-click → Extract File(s) to pull evidence out.

    Registry analysis inside Autopsy

    • Main hives at Windows\System32\config\ (SYSTEM, SOFTWARE, SAM, SECURITY, DEFAULT)
    • User hives: NTUSER.DAT and UsrClass.dat
    • Look for Run keys, Services, UserAssist, ShimCache-related data

    Always note the exact path and timestamp of anything you extract, and cross-reference with Event Logs and Splunk results.

Section 6 - SIEM

  • What is a SIEM? / SIEM Platforms
    Conceptual grounding before the hands-on Splunk work — quick but worth knowing.
  • Windows Event Logs

    The single most common data source you'll be searching through in any Windows-based incident. Core Event IDs to know:

    • 4624 — Successful logon (Type 2 = interactive, 3 = network, 10 = RDP)
    • 4625 — Failed logon (brute-force patterns)
    • 4688 — Process creation (with command-line auditing)
    • 4697 / 7045 — Service installed
    • 4720 / 4732 — Account created / added to privileged group
    • 1102 — Audit log cleared
  • Sysmon

    Dramatically richer logging than default Windows Event Logs — the tool that makes real detection possible.

    • Event 1 — Process creation (full command line + parent + hashes)
    • Event 3 — Network connection
    • Event 7 / 11 — Image load / File create
    • PowerShell 4104 — Script block logging
  • Syslog, Other Logs, Log Aggregation Explained
    Good conceptual background on how logs get centralized, less hands-on than the SIEM labs themselves.
  • SIEM Rules / Sigma
    Sigma is the portable, vendor-agnostic detection-rule format — increasingly a real industry expectation.
  • Normalization and Processing
    Behind-the-scenes SIEM mechanics — useful context, not a hands-on skill you'll be tested on directly.
  • Splunk Crash Course (Navigating, Search Queries, Search Commands, Alerts, Dashboards)

    The exact SPL skills every Splunk investigation lab assumes you already have. Always start by identifying the correct index= and sourcetype=.

    Common fields — what's in them, and why you'd check each one

    FieldWhat it holdsWhy you'd look at it
    _timeEvent timestampBuilds your timeline and lets you narrow to the incident window. Watch for odd-hour activity or gaps that hint at log tampering.
    indexWhich data repository the event lives in (e.g. wineventlog, main, firewall)Confirms you're actually searching the right data source — the wrong index means you silently miss evidence, not that there's none.
    sourcetypeFormat Splunk assigned to the data (e.g. WinEventLog:Security, sysmon)Tells you which other field names to expect — Windows Security fields look different from Sysmon or firewall fields.
    host / ComputerNameThe machine that generated the eventScopes your search to the affected host(s), and helps spot lateral movement — same account showing up on hosts it normally doesn't touch.
    EventCode / EventIDThe specific Windows event type (4624, 4688, 4625…)Your primary filter for "what kind of activity happened" — logon, process creation, account change, log clear, etc.
    Account_Name / userUsername involved in the eventFlags accounts that shouldn't be doing this — a service account logging in interactively, an unexpected admin, or a terminated employee's account.
    src_ip / Source_Network_AddressWhere the connection or logon came fromLook for external IPs on internal-only accounts, geographically odd source IPs, or one IP hitting many accounts (password spraying).
    dest_ip / DestinationIpWhere traffic or a connection went toCheck against threat intel for known-bad IPs, or watch for rare/unseen internal-to-internal destinations — a sign of lateral movement.
    src_port / dest_portSource / destination portUnusual high ports or common C2 ports (4444, 8080, 8443) are worth a second look, especially paired with an odd destination.
    Logon_TypeHow the logon happened — 2 = interactive, 3 = network, 10 = RDPType 10/3 from somewhere unexpected is far more suspicious than a Type 2 at the physical console.
    Image / New_Process_NameFull file path of the process that ranLegit software runs from Program Files/System32 — a process launching from Temp, AppData, or Downloads is a red flag.
    ParentImage / Creator_Process_NameThe parent process that spawned itMismatched parent-child pairs are one of the strongest signals you'll find — e.g. Word or Excel spawning PowerShell.
    CommandLine / Process_Command_LineThe exact command that was runWhere you actually find encoded PowerShell, download cradles, and LOLBins — read closely for -enc, IEX, DownloadString, certutil, bitsadmin.
    process_nameJust the executable name, pulled from the command lineFaster to stats/top by than the full path — good for spotting a rare process name across many hosts.
    signatureName of the alert/rule that fired (AV, IDS, correlation search)Tells you what a security tool already flagged — usually your fastest starting point/pivot into deeper manual analysis.

    Subject vs. Target — don't mix these up

    A lot of Windows Security events split "who did it" from "who/what was acted on" into two separate fields. Knowing which is which saves you from misreading an event.

    FieldWhat it holdsWhy you'd look at it
    SubjectUserName / Subject_User_NameThe account that performed the actionThe "who did it" — critical when an attacker is using a compromised account to act on a different target account (privilege escalation, account creation on someone else's behalf).
    TargetUserName / Target_User_NameThe account being logged into, created, or modifiedIn 4624/4625 this is who's logging on; in 4720/4732 it's the account being created or added to a privileged group — flags unexpected new accounts or privilege changes.
    TargetFileNameFull path of a file being created, deleted, or modified (Sysmon Event 11 FileCreate / 23 FileDelete)Where you catch a dropped payload or evidence being deleted — e.g. an executable written to Temp or AppData right before execution.
    TargetObjectThe registry key/value being modified (Sysmon Event 12/13/14)Where you catch persistence being set up — e.g. a new Run key, service entry, or Winlogon shell modification.
    TargetImageThe process being accessed or injected into (Sysmon Event 8 CreateRemoteThread / 10 ProcessAccess)Flags process injection or credential dumping — e.g. an unfamiliar process opening a handle to lsass.exe.

    Field names shift depending on the sourcetype/Technology Add-on (Windows TA fields look different from raw Sysmon XML, for example) — if a field you expect isn't showing up, check the Fields sidebar on the left of your search results, or run | fieldsummary / | top <field> to see what's actually available in that index.

    # Failed logons
index=* EventCode=4625
| stats count by Account_Name, src_ip, ComputerName
| sort -count

# Suspicious process creation
index=* (EventCode=4688 OR EventCode=1)
| search CommandLine="*powershell*" OR CommandLine="*-enc*" OR CommandLine="*IEX*" OR CommandLine="*DownloadString*"
| table _time, ComputerName, User, ParentImage, Image, CommandLine
| sort -_time

# Aggregation helpers
| stats count by src_ip, dest_ip, dest_port
| top limit=20 Account_Name
| timechart span=1h count by src_ip

# Decode a base64 command line
| rex field=CommandLine "-enc\s+(?<encoded>[A-Za-z0-9+/=]+)"
| eval decoded=base64decode(encoded)

    Investigation flow: start broad with a relevant time window → filter by EventCode or host → pivot with stats/table → tighten the time range once a lead appears.
