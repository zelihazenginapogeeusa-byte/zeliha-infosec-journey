ℹ️ How to use this tracker (click to expand)

Built for the BTL1 practical, which runs as a single ~24-hour investigation with roughly 20 task-based questions — this tracker mirrors that shape instead of a multi-host pentest checklist.

  • Everything is 100% local to your browser. Nothing here touches a server — no login, no analytics, no data collection of any kind. That also means: it's tied to this browser, on this device. Switching browsers/computers won't carry your progress over unless you use JSON Export/Import.
  • Click Start Exam Clock the moment you begin — it'll track elapsed/remaining time even if you close the tab and come back (as long as it's the same browser).
  • Rename the Q1–Q20 labels to match your actual question numbers/titles if you want it to mirror your specific exam sheet.
  • The Pace stat updates once the clock is running — remaining time ÷ open (unchecked) questions, so you always know roughly how long you can spend on what's left. It turns yellow/red as time per question gets tight.
  • Each question has an optional confidence dropdown (Low/Medium/High) — a quick way to flag which answers you should double-check before submitting.
  • Deleted a row by mistake? An Undo button appears at the bottom of the screen for a few seconds after any delete (Questions, IOCs, Timeline, Activity Map).
  • Export JSON regularly — clearing browser data, using incognito mode, or switching machines will wipe local storage. A JSON backup is the only way to recover your progress.
  • MD Report Export pulls everything you've tracked into a draft write-up using the same structure as the report template in the Blue Team study notes — it's a starting point, not a finished report.

Quick Reference / Cheat Sheet

Condensed commands and workflows so you don't have to leave this tab. Full write-ups with more context live in the Blue Team Study Notes doc.

Autopsy — quick workflow
  1. New Case → Add Data Source (disk image / E01 / raw).
  2. Select Ingest Modules — Recent Activity, File Type Identification, Hash Lookup (skip the heavy ones if time is tight).
  3. Work mainly from Keyword Search, Timeline, and Extracted Content.
  4. Right-click → Extract File(s) to pull evidence out.

Registry hives

  • Windows\System32\config\ — SYSTEM, SOFTWARE, SAM, SECURITY, DEFAULT
  • User hives: NTUSER.DAT, UsrClass.dat
  • Check Run keys, Services, UserAssist, ShimCache-related data

Log the exact path + timestamp of anything you extract — cross-reference against Event Logs / Splunk.

DeepBlueCLI — commands 
# Exported EVTX file
.\DeepBlue.ps1 .\Security.evtx
.\DeepBlue.ps1 .\System.evtx

# Bulk run across every EVTX + redirect to a file, then hunt the output
.\DeepBlue.ps1 .\evtx\* > output.txt
Select-String -Path output.txt -Pattern "sekurlsa|lsadump|Invoke-Mimikatz"
Select-String -Path output.txt -Pattern "githubusercontent|DownloadString|IEX"

# Live system (run as Administrator)
.\DeepBlue.ps1 -log security
.\DeepBlue.ps1 -log powershell
.\DeepBlue.ps1 -log sysmon

Flags: encoded PowerShell, account/group changes, service creation, log clearing, brute force, Mimikatz-style activity.

Before trusting a "clean" result — was logging even on?

A "no Mimikatz found" result means nothing if script-block logging was disabled. Check first:

Get-WinEvent -Path .\evtx\file.evtx |
  Where-Object {$_.ProviderName -like "*PowerShell*"} |
  Group-Object Id | Sort-Object Count -Descending

4104 count = 0 → script block logging was off, a blind spot. Note the gap in your answer instead of claiming a clean result.

Mimikatz strings worth searching for directly

sekurlsa:: (LSASS dump) · lsadump:: (LSA secrets/DCSync) · kerberos:: (Golden/Silver/PTT) · privilege::debug (required for LSASS access) · token::elevate · Invoke-Mimikatz (PowerSploit wrapper)

Phishing — investigation workflow

1. Defang first

http → hxxp, . → [.] before any lookup or paste.

Viewing the raw header in eM Client

  1. Open the email in eM Client
  2. Menu → View / Options / Message Details — look for "show source" or "message source"
  3. The source view contains the full header block: sender, recipients, routing path, timestamps, Authentication-Results
  4. Copy the whole header block out and work from that, rather than eyeballing it in the source pane

2. Headers

  • Trace the Received: chain bottom→top for the true originating IP
  • Compare From / Return-Path / Reply-To / Sender for mismatches
  • Check SPF / DKIM / DMARC results

Where to find the origin IP — check in this order

  1. X-Sender-IP (Microsoft EOP standard)
  2. X-Originating-IP (alternate vendor name for the same thing)
  3. Received: chain — the bottom hop is closest to the real sender
  4. Authentication-Results — sometimes carries an IP under spf=
  5. Last resort: Return-Path domain → look up its MX record and match

Reading Authentication-Results

ResultMeaning
spf=pass dkim=pass dmarc=passEnvelope is legit — still verify the content, a real account can be compromised
spf=pass dkim=fail dmarc=failAuthorized sender, but the message was tampered with or replayed
spf=failSending IP isn't authorized for that domain — likely spoofed
dmarc=pass but header.from ≠ envelope fromDomain alignment failure — check for a lookalike domain

SPF pass ≠ legitimate. A compromised real mailbox passes SPF/DKIM/DMARC perfectly because it genuinely is the authorized account — authentication proves the pipe is real, not that the sender's intent is.

3. Body & URLs

  • Identify the pretext (invoice, lockout, delivery, IT/HR helpdesk, urgency)
  • Visible link text vs. actual hyperlink; expand shortened URLs
  • Check VirusTotal / urlscan.io / AbuseIPDB / Hybrid Analysis / MXToolbox

4. Attachments

Hash (MD5/SHA1/SHA256) → submit to VirusTotal or a sandbox.

Always confirm index= and sourcetype= first — the wrong one means you silently miss evidence, not that there's none.

Two traps that quietly cost you the most time

  • | sort _time silently caps at 10,000 rows — on a big index you lose data with no warning. Use | sort 0 _time (the 0 removes the cap) or | reverse instead.
  • The same value can sit under a different field name depending on sourcetype — an IP might be DestinationIp in Sysmon, dest_ip in one TA, dstip in another. If a field search comes back empty, fall back to a raw-string search and check where it actually lives: index=* "1.2.3.4" | stats count by sourcetype.

Go-to queries

# Failed logons
index=* EventCode=4625
| stats count by Account_Name, src_ip, ComputerName
| sort -count

# Suspicious process creation
index=* (EventCode=4688 OR EventCode=1)
| search CommandLine="*powershell*" OR CommandLine="*-enc*" OR CommandLine="*IEX*" OR CommandLine="*DownloadString*"
| table _time, ComputerName, User, ParentImage, Image, CommandLine
| sort -_time

# Decode a base64 command line
| rex field=CommandLine "-enc\s+(?<encoded>[A-Za-z0-9+/=]+)"
| eval decoded=base64decode(encoded)

# Quick aggregation
| stats count by src_ip, dest_ip, dest_port
| top limit=20 Account_Name
| timechart span=1h count by src_ip

# Collapse to uniques / group into sessions
| dedup Image
| transaction host User maxspan=5m

# tstats — if the environment has CIM data models set up, this is
# dramatically faster than index=... | search since it queries the
# accelerated data model summary instead of raw events
| tstats count from datamodel=Endpoint.Registry where Registry.registry_path="*\\CurrentVersion\\Run*" by Registry.registry_path, Registry.dest

Flow: broad time window → filter by EventCode/host → pivot with stats/table → tighten the time range once a lead appears. Full field reference (incl. Subject vs. Target fields) is in the Blue Team Study Notes doc.

Stuck? Pivot ladder + 60-second reset

When a query dead-ends, work down this ladder instead of re-typing the same search — each level is harder for an attacker to evade than the one below it.

  1. Event Code / event type — you know the kind of activity (logon, process creation, file write)
  2. Parent process / context — you know what spawned what
  3. Behavioral string — you know the technique (a specific function call, a flag pattern), not just the tool name
  4. Tool-name string — last resort, breaks the moment something's renamed
  5. Time-window pivot — expand around one confirmed event on the same host/user to catch the rest of the chain

No hits? Work through this before giving up

  • Re-read the question — did you actually filter for every named entity in it?
  • Drop your most specific filter — you may have over-narrowed
  • Switch event family: 4624↔4648, Sysmon 1↔4688, 4104↔4103
  • Fall back to a raw-string search — the field name may differ by sourcetype (see the trap above)
  • Switch tool entirely — Splunk dry? Try DeepBlueCLI, Autopsy, or the raw EVTX/PCAP directly
  • Switch evidence type — no process artifact? Check Sysmon 11 (file create) or 12–14 (registry) instead
  • Mark it and move on — a later answer often hands you the anchor you were missing

No hits is a signal, not a failure — it usually means the wrong EID, field name, or assumption, not that the evidence doesn't exist.

  • 4625 — Failed logon (brute-force patterns)
  • 4648 — Logon with explicit credentials — the source-side signal for pass-the-hash; suspicious when Subject and Target accounts differ
  • 4672 — Special/admin privileges assigned at logon
  • 4688 — Process creation (with command-line auditing)
  • 4697 / 7045 — Service installed

Wireshark — workflow & FTP cookbook

⚠️ Set this first, every session: View → Time Display Format → Date and Time of Day. Wireshark defaults to relative time — any "what time did X happen" question is unanswerable until you change this.

Where to look before you write a single filter

  1. Statistics → Protocol Hierarchy — what's actually in the capture
  2. Statistics → Conversations — top talkers; sort by bytes for exfil, by packets for scans
  3. Statistics → Endpoints — per-host traffic volume
  4. Right-click → Follow → TCP/HTTP/TLS Stream — full session reconstruction
  5. File → Export Objects → HTTP/SMB/IMF/TFTP — pull the actual files out
  6. Statistics → Expert Information — anomalies Wireshark already flagged for you

Files transferred over non-HTTP won't show up in Export → HTTP — check the SMB, IMF (email), and TFTP submenus too. HTTPS content can't be exported without the session key.

FTP investigation cookbook

  1. Filter ftp to isolate the command channel
  2. Scan for USER, PASS, RETR, STOR, LIST
  3. Follow TCP Stream on any 230 (login OK) response for the full session
  4. Brute force? Count PASS attempts from one source
  5. Exfil? Find RETR, then trace the separate data-channel connection
  6. Hash any retrieved file via Export → then sha256sum

Sysmon Event IDs
  • Event 1 — Process creation (full command line + parent + hashes)
  • Event 3 — Network connection
  • Event 7 / 11 — Image load / File create
  • Event 8 / 10 — CreateRemoteThread / ProcessAccess (injection, credential dumping off lsass.exe — watch for GrantedAccess 0x1010/0x1410)
  • Event 12 / 13 / 14 — Registry create/modify/rename (persistence via Run keys)
  • Event 22 — DNS query
  • PowerShell 4104 — Script block logging (4103 = module logging, weaker signal)

Final 60 minutes — verify ritual

Run this on every single answer, top to bottom, before you submit:

  • Does the answer match the exact format asked for — hash type, date format, IP, filename, MITRE ID?
  • No typos — hashes, filenames, IPs, domains copy-pasted, never retyped
  • Timestamps in the right format and the right timezone
  • Sub-techniques used where one applies (T1110.003, not the bare T1110)
  • Every question attempted — a partial answer beats a skipped one
  • No leftover scratch text sitting in an answer field
  • Capitalization matches the source, not your memory of it

The smell test: for anything that came easily, ask "did I verify this, or just pattern-match it?" — if the latter, do one more corroborating pivot. For anything that came hard, re-read the question one final time and check the format again. Once every box is checked once, stop — a defended answer beats an endlessly re-polished one.
